# Independent runtime and method audit

30 September 2026. Read-only review by `/root/external_runtime_audit`; no model execution, training, cloud access, installation, or Git mutation. This report distinguishes source evidence, saved execution receipts, and unmeasured mechanisms. Local tokenizer verification and one existing artifact-free unit test were executed.

## Findings

1. **The exact current Gemma evaluation wrapper differs from its historical training wrapper.** `cloud_pilot/bundle.py:37-39` defines an English translation instruction followed by `Source:`; `bundle.py:129-143` renders it as one user message, masks the complete prompt, and supervises the target plus `<turn|>\n`. Current `dev_assisted.messages` instead returns `palref_eval.SYSTEM` as a system message plus `CAUTION` and a JSON object containing `source_text` and an empty `examples` list (`cloud_pilot/dev_assisted.py:32-35,92-98`; system at `palref_eval.py:20-21`). Both old and corrected mixed training preserve the historical instruction for historical rows and use separate auxiliary task instructions (`experiments/mixed-supervision-20260929/prepare.py:108-121,134-144`; `experiments/training-ready-v2-20260929/prepare.py:53-86`). Calling all training "bundle.PROMPT" would omit those auxiliary tasks. Calling the evaluation wrapper "never trained" is supported only for this project's fine-tuning examples, not the publisher's unknown pretraining/instruction data.

2. **A changed chat-template version or thinking flag is not established.** Both pathways use the frozen tokenizer hashes and `enable_thinking=False`, `add_generation_prompt=True` (`bundle.py:32-35,131-143`; `dev_assisted.py:165-176`; `contextual_run.py:164-175`). The template itself adds a system turn only when supplied and ends the generation prefix with an empty thought channel when thinking is disabled (`resources/local/cloud-pilot-qualified-20260927/tokenizer/chat_template.jinja:188-215,382-385`). Thus system/user structure is a real prompt difference; an unexpected thinking mode is not supported by the audited source.

3. **NF4 training versus BF16 evaluation is real, but it is not FP32 evaluation and not yet an explanation of failure.** Mixed training loads NF4 with double quantization and BF16 compute, applies `prepare_model_for_kbit_training`, then loads trainable step280 LoRA (`cloud_pilot/mixed_run.py:189-195`). Evaluation deletes that model, loads the publisher base in BF16 without quantization, and restores the exact candidate adapter (`mixed_run.py:207-217`). This changes the frozen numerical backbone; the saved adapter is checked tensor by tensor, including dtype and shape (`contextual_run.py:259-271`). No same-checkpoint, same-prompt paired NF4/BF16 quality contrast was found. Do not describe BF16 as intrinsically invalid for QLoRA or assume NF4 will improve quality.

4. **The 96-step runs deliberately restarted the optimizer and LR schedule.** They load step280 adapter weights but call a new Trainer with fresh AdamW state, a linear schedule, LR `1e-4`, four warmup steps, and 96 updates (`mixed_train.py:16-17,88-92,137-148`; AdamW settings at `contextual_train.py:16-18`). The saved old and corrected `recovered/mixed/training/run.json` each report `status=completed`, `completed_steps=96`, `fresh_optimizer=true`, 1536 consumed slots and the same initial adapter tensor digest `df16670b3b7bfc24da89c91724849d297b4b0a1db6298f1e8be16d1a62a53014`; final digests differ. This supports an intentional new optimization phase, not lost weights or failed checkpoint resume. The actual per-step LR is not in the mixed progress ledger, so the exact peak is established by configuration/scheduler source rather than an independently logged LR trace. Qualified canary-to-step280 training instead calls `trainer.train(resume_from_checkpoint=...)` (`runtime.py:319`) and its saved 280-step trainer history has continuous LR decay. The concern therefore applies to the mixed/contextual continuation design, not every training/resume.

5. **None of these concerns generalizes automatically to NLLB.** Its encoder receives tokenized raw source, with a language token and forced Persian BOS for decoding, without the Gemma chat wrapper (`nllb_train.py:251-255`). It uses FP32 trainable parameters and BF16 autocast rather than Gemma NF4/LoRA (`nllb_train.py:75-84,303-308`). Its 700-update schedule and optimizer restoration are separate code paths. Gemma prompt/quantization explanations cannot explain NLLB's results without separate evidence.

6. **F11 is a confirmed metadata defect.** `mixed_run.py:174` hardcodes `experiment_id='mixed-supervision-20260929'`; corrected `experiments/training-ready-v2-20260929/recovered/mixed/run.json:2` contains that old label. The launcher admits `manifest.version='corrected-v2'` (`hf_mixed.py:218-221`), and data/adapter hashes remain distinct. Derive the emitted identity from the validated data version, preserve the original receipt, and add a corrected-version identity check. This does not establish that the wrong dataset was trained.

7. **F12 is a confirmed legacy reproduction failure.** Direct invocation of `python -B -X utf8 -m unittest cloud_pilot.test_dev_evidence.DevEvidenceTests.test_actual_frozen_build_complete_provenance_and_expected_coverage` returned one error in0.002s: `dev_evidence.py:117`, `Frozen source helper differs: bundle.py`. The pin at line20 is `9721bcb...`; it exactly matches the retained original `resources/local/cloud-pilot-20260926-hf-v5/bundle.py`. Current `cloud_pilot/bundle.py` is `600947...`, exactly matching the qualified20260927 helper. This is shared-helper version drift in a legacy original-TRAIN evidence builder. A minimal current-code repair is to review helper behavior, update the live pin, and prove reconstructed evidence records remain identical; alternatively bind the legacy builder to its exact retained helper. Never overwrite the historical audit/receipt to make it appear originally generated under the new source hash. The production plain evaluator reads frozen evidence and does not call this builder, so this failure is not a demonstrated explanation for the completed translations.

## Fresh local tokenizer check

On the first frozen DEV source, exact rendering and explicit `return_dict=False` tokenization agree: canonical train67 tokens, old PAL-REF evaluation105 tokens, current plain182 tokens. Each has one BOS and the same final model/empty-thought-channel suffix. All28 learning diagnostic prompts exactly reproduce their original selected mixed-pool prompt token prefix. These are tokenizer/serialization checks only, not inference. An initial audit harness omitted explicit `return_dict=False` and compared a returned mapping to a list; the corrected check used the production argument and passed. That harness mistake is not a repository defect.

## Smallest clean inference contrast for the review's two numerical/prompt hypotheses

First decide the question. Learning28 asks whether original task records can be reproduced; a DEV prompt/precision contrast asks whether the evaluation interface suppresses existing translation ability. Neither tests the causal effect of resetting LR/optimizer, and neither should be relabeled as the other.

The smallest first stage is **prompt only at fixed BF16**, on one predeclared checkpoint (corrected96 if it is the current candidate), using existing24 source-only DEV cases and15 whole/9 constrained split. Compare the canonical historical training prompt with the exact current plain wrapper; keep every other condition fixed. This requires24 new outputs if the existing24 BF16/plain outputs meet the reuse conditions below. It estimates this checkpoint's prompt effect without answering precision. Do not change precision in the same first-stage comparison.

If a separate precision question remains worth measuring, freeze its follow-up criteria before seeing the first-stage scores. The complete crossed design below measures both factors and their interaction:

| | Canonical historical training prompt | Exact current plain wrapper |
|---|---|---|
| Recreated training NF4 numerical path |24 outputs|24 outputs|
| Publisher BF16 base plus same adapter |24 outputs|24 outputs|

This is96 condition slots for one checkpoint. It is the smallest full-factorial design that estimates both differences and their interaction over the existing complete panel. Reuse the24 cached BF16/current-wrapper outputs only if checkpoint, tokenizer/rendered token hashes, package/runtime, decoding, cap/deadline policy, and source identities match; otherwise record the new run as a replication. A smaller preselected source panel is a smoke diagnostic, not the full merit estimate. Comparing NF4/training prompt directly with BF16/current wrapper alone confounds both factors.

Freeze checkpoint and base hashes, adapter dtype/tensors, token IDs, seed, eager attention, greedy decoding, output/time caps, fresh context/cache and failure denominator. Recreate the training NF4 path including nonquantized dtype changes made by k-bit preparation; merely adding an NF4 loading flag can define a different numerical condition. Then disable training/gradients/checkpointing for inference and verify the adapter is unchanged. At each load, compare cached/uncached next-token logits on a short fixed probe as a numerical check, separately from translation merit. Counterbalance prompt order and checkpoint order if more than one checkpoint is later included. Blind the outputs and preserve both reviewers' judgments, critical errors and failure slots.

This establishes a within-checkpoint interface effect only. To conclude that a different interface reverses the ranking of qualified280 and corrected96, repeat the same crossed conditions for qualified280; current cached BF16/plain ranking is not enough to infer the other cells. LR/optimizer causality still requires a separately authorized matched training comparison, not inference.

## Audit conclusion

The external review identifies genuine interface and experimental-design differences, but the available receipts do not establish them as the dominant failure mechanism. Two minor reproducibility/identity defects (F11/F12) were confirmed; no new demonstrated generation or optimizer corruption emerged in this bounded audit. The strongest next action is a small preregistered inference test chosen for one concrete unresolved question, after reconciling the existing learning28 candidate identity. More training is not required to obtain that measurement.
