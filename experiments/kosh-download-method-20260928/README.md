## Why 100 does not provide exhaustive paging

[Kosh API documentation](https://kosh-docs.vercel.app/apis) documents search and lookup by known IDs. The [published REST implementation](https://github.com/cceh/kosh/blob/a79cd742e9140b42aa7b5beb1050b8cbd5eca53e/kosh/api/restful.py) accepts field, query, query_type and size. The [search implementation](https://github.com/cceh/kosh/blob/a79cd742e9140b42aa7b5beb1050b8cbd5eca53e/kosh/elastic/search.py) takes the first size matches and exposes no offset, cursor, total count or complete-ID enumeration. This is source-code evidence; the production revision is unknown. The published code can also convert backend search exceptions into empty results, so an empty batch alone cannot certify completion.

The [published client](https://github.com/cceh/kosh_client/blob/3ab9aa9d56e83e9a80694646e16ea6ab3037e888/src/utils/fetchResults.js) issues separate asynchronous requests for selected dictionaries. Selecting all 31 can create many simultaneous requests. Its [display controls](https://github.com/cceh/kosh_client/blob/3ab9aa9d56e83e9a80694646e16ea6ab3037e888/src/components/ResultParams.js) only change rendered columns. These findings do not establish the cause of the earlier 403/500 responses or a safe server rate.

Repeating an unchanged size=100 query can retrieve the same records. A smaller result cap reduces response size but does not guarantee that a broad wildcard query is inexpensive. Searching different fields can overlap records and omit entries with missing fields. IP changes do not resolve these completeness problems.
